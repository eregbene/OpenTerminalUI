# QuantConnect/LEAN vs. Bensim — Gap Analysis

**Date:** 2026-08-21
**Scope:** Bensim's live MT5 forex trading system — `backend/mt5_strategies/`, `backend/historical_intelligence/`, `backend/adaptive_management/`, `backend/portfolio_execution/`, `backend/market_structure/`, `backend/decision_context/`, `backend/economic_intelligence/`, `backend/brokers/mt5/`. Equities/crypto/options code (`backend/model_lab/`, `backend/robustness/`, `backend/portfolio_lab/`, `backend/research*/`, `backend/core/statlab/`, `backend/core/single_asset_backtest.py`) is treated only as *evidence of latent capability*, not as part of the live system, since it is being removed in an unrelated cleanup and — confirmed by grep against `backend/api/router.py` — is not even wired into the current API.
**Method:** Direct source reading (not file-name inference) of the modules above, the two prior honest audits in this repo (`docs/HISTORICAL_INTELLIGENCE_AUDIT.md`, `docs/HISTORICAL_INTELLIGENCE_PERSISTENCE_AUDIT.md`), the root-level `scratch_*.py` research scripts, plus current QuantConnect documentation (quantconnect.com/docs) and the LEAN GitHub repository. Where a LEAN implementation detail could not be confirmed with confidence from docs/repo, that uncertainty is stated explicitly rather than guessed.
**Out of scope, not touched or discussed as a target of change:** the cTrader broker-independence migration, and nothing in this document should be read as a mandate to modify `backend/brokers/mt5/`, `backend/mt5_strategies/`, `backend/historical_intelligence/`, `backend/portfolio_execution/`, or `backend/adaptive_management/`. This is research only — no code was written or changed.

---

## 0. One-paragraph summary

Bensim's actual live system has two faces that a superficial "QuantConnect has X, does Bensim?" pass would miss entirely. First, its domain-specific historical-analog engine (`backend/historical_intelligence/`) is genuinely sophisticated and, in places, *more conservative and more forex-execution-aware* than what LEAN provides out of the box: point-in-time bar integrity with an explicit source hierarchy, strict no-lookahead enforcement with a regression test asserting it, effective-sample-size-with-clustering (never inflating evidence), purge/embargo walk-forward, and a directional-edge taxonomy that separately labels "reliably negative" from "unstable." Second, a *disconnected* subsystem (`backend/model_lab/`, `backend/robustness/`, `backend/research_autopilot/`) already contains real Deflated/Probabilistic Sharpe Ratio math (Bailey & López de Prado), block-bootstrap Monte Carlo, and walk-forward folds — but it is wired to a vectorized equities backtester (RELIANCE/NSE defaults, flat-bps costs) that has never touched an MT5 strategy and is not even registered in `backend/api/router.py` today. The single most consequential genuine gap is not "Bensim lacks statistics" — it does not — it is that **Bensim's own historical-outcome labeling has no realistic fill/spread/commission model**: `outcomes.py` resolves SL/TP against M15 bar highs/lows with spread cost applied only when a live decision snapshot happened to capture it, and commission is deliberately never estimated. Every R-multiple, every walk-forward result, every ESS number currently gating live influence is computed on *gross*, not net-of-realistic-execution-cost, outcomes for the large majority of the corpus. That is the highest-value fix available, and it does not require adopting any LEAN infrastructure to close — it requires extending the module Bensim already owns.

## 1. Backtesting engine

Bensim does not have one "backtesting engine" — it has three, serving different purposes, none of which is an order-lifecycle/fill-state-machine simulator in the LEAN sense.

- **The system that actually matters for live decisions**: `backend/historical_intelligence/replay.py` + `outcomes.py`. This replays the *exact* production strategy functions (`mt5_strategies.context.build_strategy_context`, `families.evaluate_all`, `fusion.build_candidates`, `autonomous._score_candidate` — imported directly, never reimplemented) against point-in-time-safe candle history (`bars_as_of`, three-tier source hierarchy: decision snapshot → revision-tracked reconstruction → legacy fallback). Strict no-lookahead is enforced in one place and has a dedicated regression test (`test_bars_as_of_never_returns_future_data`). This is real strategy-signal parity, and it is Bensim's actual strength — LEAN cannot replicate "did our real production code fire this signal" without literally running Bensim's own strategy code inside it.
- **What it does *not* do**: simulate an order book, a fill state machine, partial fills, or realistic entry slippage. `outcomes.py` resolves outcomes by scanning forward M15 bars and checking `high`/`low` against SL/TP levels — a bar-touch model, not a tick/quote-level fill simulation. When both SL and TP are touched inside the same M15 candle, the code deterministically resolves SL-first (documented, matching the live shadow resolver's own convention) — a conservative tie-break, not a modeled intrabar path. Entry price during replay is the M15 close with spread assumed zero unless a real decision snapshot supplied bid/ask (`replay.py`'s own docstring: "approximated ... unless the caller supplies a real historical tick or a decision snapshot"). There is no partial-fill concept anywhere in this pipeline (MT5 forex market orders normally fill in full or not at all, so this specific absence is low-value to fix).
- **Cost realism in outcome labeling is optional, not default.** `_net_r()` in `outcomes.py` only computes a net-of-spread R-multiple when `real_spread` is supplied — and it is only reliably supplied when a decision snapshot exists (i.e., for MT5-native corpus entries near the live path, not for the much larger ForexSB deep-history backfill). Commission is *explicitly, deliberately* never estimated in this module ("would require a lot-size/pip-value assumption this module has no honest basis for"). The consequence: the walk-forward `expectancy_r` numbers gating live influence today (`historical_walk_forward_results`, e.g. `mtfai1` at n=41,387, OOS expectancy −0.085R) are **gross-of-cost** for most of the corpus. A strategy sitting near breakeven gross could be reliably negative net of realistic spread+commission and the current gate would not see it.
- **The separate generic engine** (`backend/core/single_asset_backtest.py`, driving `backend/model_lab/`) is a vectorized single-asset engine with a flat fee+slippage-bps cost model and an integer fill-delay-in-bars — genuinely simpler than LEAN's event-driven engine, but it is not used for MT5 strategies at all (confirmed: `backend/services/backtest_jobs.py` has zero MT5 references; its defaults are NSE/BSE/RELIANCE).
- **Multi-symbol/multi-timeframe synchronization**: the replay path fetches M15/H1/H4 per-symbol independently at a shared `at` instant — correct for single-candidate replay, but there is no cross-symbol simultaneous-clock backtest (e.g., "run all 10 forex pairs through one synchronized clock and watch portfolio-level margin/exposure evolve tick-by-tick") anywhere in the codebase. This only matters if Bensim ever wants to *backtest* (not just live-monitor) portfolio-level risk across correlated pairs — see §4.
- **Warm-up / missing / stale data**: handled conservatively and well. `bars_as_of` explicitly excludes any bar that cannot be proven "knowable at `at`" rather than guessing; `_MIN_BARS` thresholds gate a replay entirely (`INSUFFICIENT_HISTORY`) if warm-up data is short. This is arguably stricter than LEAN's `SetWarmUp` (which has documented gaps, e.g. it silently does not work under universe selection).

**Where Bensim is weaker than LEAN:** no realistic fill/spread/commission model in offline outcome labeling (the actual, material gap); no tick/quote-level intrabar path reconstruction (LEAN can consume tick or second-resolution data — Bensim only has OHLC bars for forex history); no portfolio-level synchronized multi-symbol backtest loop.
**Where Bensim is comparably strong or stronger:** point-in-time integrity (Bensim found and fixed two real historical bugs — bar-overwrite and broker-UTC-offset — that a generic engine like LEAN would not have been exposed to at all, since LEAN's own data pipeline is different); no-lookahead enforcement is a single audited chokepoint with a named regression test, not "documentation says the engine avoids lookahead."

## 2. Validation and anti-overfitting

This is the area where "inspect first" mattered most — Bensim already has real, correctly-implemented machinery LEAN doesn't ship as a default report, sitting in a currently-disconnected module.

- **Walk-forward, chronological, with purge/embargo**: `historical_intelligence/walk_forward.py` implements a real train/OOS split (default 60/40) with a documented 12-hour purge window sized against the outcome-labeling lookforward horizon, explicitly to prevent a train-window setup's outcome from leaking future information into the OOS window. This is conceptually equivalent to (and, because it's purpose-built against Bensim's own outcome-resolution horizon, arguably better calibrated than) LEAN's generic walk-forward optimization, which QuantConnect's own docs describe primarily as a parameter-re-tuning technique, not a leakage-safety mechanism.
- **Directional-edge classification, separate from retention**: `classify_directional_edge` distinguishes "reliably negative in both windows" (real, actionable) from "unstable / sign-disagreement" (no reliable conclusion) — a genuinely useful taxonomy LEAN has no equivalent concept for, because LEAN has no notion of a "historical analog pattern" at all; its walk-forward is about re-fitting strategy *parameters*, not classifying the reliability of a discovered pattern.
- **Effective sample size, not raw N**: `similarity.py`'s ESS construction (similarity-weighted, ≥0.6 threshold, 6-hour temporal-cluster dedup collapsing correlated neighbors to one representative) is a real, tested (`effective_sample_size <= raw_neighbor_count` is an asserted regression test) defense against exactly the "one sustained trend counted as dozens of independent confirmations" failure mode. This is more specific and more conservative than anything QuantConnect ships by default.
- **Deflated Sharpe Ratio / Probabilistic Sharpe Ratio / minimum track record length**: `backend/robustness/scorecard.py` is a correct, well-cited (Bailey & López de Prado 2012/2014) implementation — PSR, DSR with a multi-trial correction via the expected-maximum-Sharpe-under-N-trials formula, block-bootstrap confidence intervals on Sharpe/CAGR/Sortino/max-drawdown, and a `verdict` classifier (`robust`/`fragile`/`overfit`/`insufficient`) with explicit reasons. **This exceeds what LEAN's own backtest report ships by default** — LEAN/QC Cloud computes a rolling PSR on its report, but does not appear (from current docs) to apply a multi-trial DSR correction automatically; that is normally something quants bolt on themselves, which Bensim has already built. The catch: `compute_robustness` is called only from `research_autopilot/service.py`, which runs against Yahoo-fetched cross-sectional equity panels, never against MT5 strategy R-multiple series. **It has never been run on a single Bensim forex strategy's actual trade sequence.**
- **Monte Carlo / bootstrapping**: `backend/model_lab/montecarlo.py` implements both i.i.d. and moving-block bootstrap resampling of trade returns, producing confidence cones, terminal-wealth percentiles, and worst-case-drawdown percentiles — again, real and correct, again never applied to an MT5 strategy's trade sequence. `robustness/scorecard.py`'s own bootstrap is separate and simpler (metric-summary CIs only, no path/drawdown cones). Neither has ever been pointed at `historical_setup_outcomes` or at a live strategy's real closed-trade R sequence.
- **Multiple-hypothesis testing / selection bias**: partially addressed. DSR's `num_trials` parameter exists precisely for this, but nothing in the live pipeline currently tracks "how many strategy variants / parameter sets / threshold tweaks were tried before this one was kept" to feed that parameter honestly. Bensim's strategy set (11 families, each essentially hand-designed once) has less multiple-testing exposure than a typical parameter-sweep-heavy quant shop, but the `_MIN_SAMPLE_FOR_LIVE_INFLUENCE = 100` / ESS≥100 bar is itself a form of implicit multiple-testing protection (a high fixed evidence bar rather than a correction term) — a reasonable, if less formal, substitute.
- **Probability of ruin / drawdown distributions**: not computed for MT5 strategies anywhere. `walk_forward.py::_stats_for_rows` computes a simple sequential cumulative-R drawdown (a real number, not simulated) but no Monte Carlo drawdown *distribution*, no probability-of-ruin estimate under position-sizing assumptions. `model_lab/montecarlo.py`'s `worst_case_drawdown` percentile output is exactly this concept, again unapplied.
- **Cross-regime / cross-timeframe validation**: `walk_forward.py` accepts `regime`/`session`/`confidence_band` filters and `segment_matrix.py` (not read in full here, but named and tested) exists specifically for a strategy×symbol×regime breakdown — this is real cross-regime validation infrastructure, more granular than LEAN's out-of-the-box tooling (LEAN has no first-class "regime" concept; a user would hand-write this).
- **Look-ahead bias / data leakage**: covered above (§1) — this is a genuine Bensim strength, actively audited and regression-tested, not a gap.
- **Cross-market validation**: N/A in a useful sense — Bensim trades one asset class (forex) across correlated pairs, not genuinely independent markets; LEAN's cross-asset-class validation tooling (equities vs. futures vs. crypto) has no natural analog here and would not add real value.

**Net assessment:** Bensim's *validation math* is not behind LEAN's — in the DSR/PSR/bootstrap dimension it is ahead of LEAN's default reporting. The gap is 100% an application gap: none of this machinery has ever been run against a real MT5 strategy's actual outcome sequence. That reframes "adopt walk-forward/Monte Carlo/DSR from LEAN" into "wire the walk-forward/Monte Carlo/DSR code Bensim already wrote to the strategies that actually trade" — a much smaller, much higher-confidence piece of work than building or integrating a new engine.

## 3. Optimization

- **Grid search / parameter sweep**: exists (`model_lab/service.py::param_sweep`, capped at 96 combinations, ranked by Sharpe then return) — again on the disconnected equities engine, never run against an MT5 strategy's parameters. LEAN Cloud's own optimization strategy roster is, per current docs, **grid search only** ("Grid search is the only strategy currently available" — QuantConnect's own optimization-strategies page, checked directly) — genetic/Bayesian optimization are *not* shipped by QuantConnect Cloud today despite being commonly assumed. This matters: the popular belief that "QuantConnect has advanced optimization" is not accurate as of this check; it has the same brute-force grid Bensim already has code for.
- **Random search, Bayesian optimization, evolutionary/genetic optimization**: neither Bensim nor LEAN/QC Cloud has these today (LEAN's GitHub issue tracker shows walk-forward-optimization and alternative-strategy requests as open community asks, not shipped features). Not a real gap to close by copying QuantConnect, since QuantConnect doesn't have it either.
- **Multi-objective / Pareto**: Bensim's `model_lab/service.py::compare()` already computes a Pareto frontier over (total_return, max_drawdown) across runs — real, working code, unapplied to MT5.
- **Robustness-favoring optimization (the user's explicit concern — not curve-fitting)**: this is the one place where a genuine, not-yet-built capability exists on both sides. Neither Bensim's `param_sweep` nor LEAN's grid search penalizes a narrow, unstable optimum vs. a wide, stable "plateau" — both simply rank by best point-estimate metric (Sharpe/return). Building a **parameter-plateau / stability-surface report** (does performance stay acceptable across a neighborhood of each candidate parameter set, not just at the single best point) is a real, currently-missing capability on both sides, and one Bensim should build itself rather than expect from LEAN, since LEAN doesn't have it either.
- **Sharpe/Sortino/drawdown-constrained optimization**: Bensim's sweep ranks by Sharpe/return only today; no drawdown-constrained variant exists yet (would be a straightforward addition to the existing sweep code, not a new capability class).

**Net assessment:** optimization is a wash, not a Bensim deficiency vs. LEAN — QuantConnect's marketing/reputation implies more sophistication here than the actual shipped product has. The one real, unmet need (robustness-favoring / plateau-aware optimization) is a native build either way.

## 4. Portfolio simulation

- **Live portfolio accounting is genuinely mature**: `backend/portfolio_execution/service.py` computes real margin, free margin, margin-level, margin-utilization, exposure-by-currency/symbol/strategy/direction/timeframe/session, and a live `CorrelationEngine` correlation matrix (driven by real broker account data across the 25K/50K/100K sub-accounts), plus FX conversion rates for cross-currency exposure netting. This is not a toy — it is comparable in scope to what LEAN's portfolio object exposes, and it has the advantage of being computed from the *actual* live broker account state rather than a simulated one.
- **What's missing is the historical/backtested version of the same thing.** All of the above is computed live, forward-only, from the current account snapshot — there is no mechanism to replay this same margin/exposure/correlation accounting *backward in time* across a multi-position historical simulation (e.g., "if all 4 demo accounts had been running this strategy mix for the last 6 months, what would portfolio-level margin utilization and cross-pair correlation exposure have looked like at each point in time"). LEAN's portfolio object is available inside a real event-driven backtest loop, so this kind of retrospective portfolio-level view falls out of the engine naturally; Bensim would have to build it deliberately since there is no backtest loop to hang it on.
- **Buying power / leverage / margin models**: MT5's real margin behavior is used live (`order_calc_margin` calls into the actual broker), which is more accurate than any simulated model for the live-execution question — but it means there is no way to *backtest* what margin usage would have been under a hypothetical parameter change without actually running it live or building a standalone margin simulator.
- **Concentration / risk budgeting**: `MAX_MARGIN_UTILIZATION` and `MAX_CORRELATED_EXPOSURE` blockers exist and are enforced live (`portfolio_execution/service.py`) — real, working risk budgeting, just live-only, not offered as a backtest constraint.
- **Position sizing**: `brokers/mt5/risk_calculator.py` / `risk_budget.py` (not read in full for this document, but present and referenced throughout `autonomous.py`) implement real position sizing tied to account risk percentage; this is functionally comparable to what a LEAN `PortfolioConstructionModel` would do, just not built on the generic Algorithm Framework abstraction.
- **Multi-currency accounting**: handled live via `_fx_conversion_rate` — correct for forex (all instruments are inherently multi-currency), but again live-only.

**Net assessment:** live portfolio/margin/correlation accounting is a Bensim strength (D — already adequate) built directly against real broker semantics. The genuine, non-superficial gap is the *retrospective/backtested* view of the same accounting — something LEAN gets for free from having an event-driven loop, and something Bensim would have to deliberately build (native, not LEAN-shaped) since it doesn't have — and does not obviously need — a general-purpose backtest loop to hang it on.

## 5. Execution simulation

- **Live execution cost accounting is real and correct**: `brokers/mt5/trading_costs.py` is a single, audited source of truth for `net_pnl = gross_pnl + commission + swap + fee`, with a documented, broker-verified sign convention and an explicit `BROKER_REPORTED` vs `CONFIG_FALLBACK` distinction so a real $0 commission is never confused with a missing value. This is exactly the kind of real-accounting rigor LEAN's fee models exist to provide, and Bensim's version is grounded in actually-observed broker deal data rather than a modeled assumption.
- **Only market orders exist.** Grep-confirmed: `MT5ExecutionService` exposes `submit_market_order` and no pending-order (limit/stop/stop-limit) submission path. For a forex demo/live strategy set built around immediate structural entries (BOS/CHoCH retests, breakout confirmation, etc.) this is a reasonable, deliberate design choice, not an oversight — market orders are what these strategies actually want. It becomes a real gap only if a future strategy family wants to enter on a limit retracement rather than a confirmed break, which none currently do.
- **No fill model, no slippage model, in the backtest/replay sense** — covered in §1: `outcomes.py` never simulates a fill price different from the bar's implied touch level, and the near-zero-cost approximation dominates the corpus. This is the same gap restated from the execution-simulation angle: Bensim's *live* execution is well-instrumented after the fact, but its *historical* execution simulation assumes free, instant, spread-free fills for the vast majority of replayed setups.
- **Order state machine**: live order lifecycle (submit → check margin → filled/rejected, via `order_check`/`submit_market_order`/`classify_retcode`) is real and MT5-broker-accurate, but it's a thin wrapper around MT5's own synchronous market-order semantics — there's no independent state machine to speak of because MT5 market orders don't have one. This is not really comparable to LEAN's `ITransactionHandler`, which exists because LEAN supports many order types and many brokers with different fill semantics; Bensim's simpler live wrapper is appropriately simple for what it actually does.
- **Rejected orders / partial fills / async fills / order modification / cancellation**: retcodes are classified (`classify_retcode`) so rejections are handled; partial fills are not a meaningful MT5-forex-market-order concept; order modification exists for SL/TP adjustment (adaptive_management's domain, out of scope here) but not for pending-order price modification, consistent with market-orders-only.
- **Latency assumptions**: not modeled anywhere, live or historical. MT5's real round-trip latency (order submit → broker ack) is not tracked as a distribution and not injected into replay. Low priority: at M15 strategy timeframes, realistic MT5 demo-account latency (tens to low hundreds of ms) is immaterial to outcome relative to the spread-cost gap above.

**Net assessment:** the single highest-value, most concretely evidenced gap in this entire document is here: **spread and commission cost realism in historical outcome labeling.** It is a small, well-scoped fix (the module and the exact functions to extend already exist — `outcomes.py::_net_r`, `label_outcome`), not a request to adopt any part of LEAN's fill-model machinery.

## 6. Data infrastructure

Historical Analog Intelligence's data layer is explicitly out of scope for replacement per the task brief, and nothing below suggests replacing it — this section evaluates infrastructure *quality*, not the analog-intelligence *feature* itself.

- **Normalization / point-in-time integrity**: genuinely strong, arguably stronger than a generic engine would provide by default, precisely because it was built to fix two real bugs Bensim's own operational history surfaced (bar-overwrite via `db.merge()`, broker-server-time-vs-UTC). LEAN's data pipeline has its own well-tested normalization for its own supported vendors, but it has no exposure to *MT5's specific* timestamp/overwrite failure modes — this is not a capability gap, it's a different (and necessarily narrower) problem Bensim solved for its own broker.
- **Resolutions**: M5/M15/H1/H4/D1 supported; no tick or second-resolution forex data anywhere in the corpus. LEAN supports tick resolution generally, but for forex specifically LEAN's own out-of-the-box data is typically quote/bar (not exchange tick, since forex has no consolidated tape) — so this is a smaller gap than "LEAN has ticks, Bensim doesn't" implies; the realistic comparison is bar-vs-bar, and the delta is mainly Bensim's M15 granularity vs. finer M1 bars, which would materially improve the SL/TP tie-break precision noted in §1.
- **Time zones / broker-server-time handling**: handled correctly and explicitly (the UTC-offset fix above); LEAN's time zone handling (exchange-time-zone-aware consolidation, algorithm-time synchronization across multiple exchange time zones) is more general-purpose but forex has no exchange calendar in the equity sense (24/5, one global session structure) — LEAN's exchange-calendar machinery is built for equity/futures market-hours edge cases (holidays, half-days) that mostly don't apply to Bensim's instrument set. `market_structure/sessions.py` already encodes the forex session structure (Asian/London/NY) Bensim actually needs.
- **Symbol mapping / corporate actions**: not applicable to spot forex (no splits, dividends, ticker changes) — correctly, this is simply absent from Bensim because forex doesn't need it, not a gap.
- **Consolidators / resampling**: ForexSB backfill derives H1/H4/D1 from native M30 "gap-safely (no fabrication across gaps)" per the audit — a real, working consolidation path, purpose-built rather than generic. LEAN's generic `TradeBarConsolidator`/calendar consolidators are more reusable in the abstract but solve the same problem Bensim has already solved for its own two providers (MT5, ForexSB).
- **Provider reconciliation**: `ingestion.reconcile_providers` / `quality.compare_provider_overlap` (NO_OVERLAP/CONSISTENT/DIVERGENT/INCOMPATIBLE classification) is a real, working, tested cross-provider data-quality mechanism with no obvious LEAN equivalent — LEAN assumes one data vendor is authoritative per asset, it doesn't cross-validate two independent historical sources against each other the way Bensim's ForexSB-vs-MT5 reconciliation does. This is a genuine Bensim strength.
- **Streaming / caching**: Redis-fronted (`cache.py`/`adaptive_cache.py`), fail-open, versioned keys — solid, standard design.
- **Storage**: Postgres for durable results; the persistence audit found real gaps here (container-local JSON backtest results with no volume mount, at genuine risk of loss on rebuild) — this is an operational gap already identified and tracked in this repo's own audit, not something LEAN's architecture is relevant to.

**Net assessment:** no LEAN data-infrastructure capability rises to "materially improves Bensim" here. The honest gap that exists (finer-than-M15 forex bar resolution for tie-break precision) is a data-acquisition question (does a provider offer cheap M1 forex history), not an engine-architecture question LEAN answers.

## 7. Research tooling

- **Confidence calibration / threshold sensitivity is already built**: `brokers/mt5/confidence_calibration.py` (grep-confirmed) implements `calibration_reliability_report`, `component_effectiveness_report`, `ranking_quality_report`, `rejection_analysis_report`, and `threshold_simulation_report` — this is genuinely good diagnostic tooling most retail/quant setups don't build until much later, and it is specific to Bensim's own ranking-score architecture in a way no generic LEAN report could be.
- **MAE/MFE tracking**: already computed per-outcome in `outcomes.py` (`mfe_r`, `mae_r`, time-to-milestone tracking at 0.25/0.5/0.75/1/1.5/2R) — real, working, arguably more granular than LEAN's default report (LEAN doesn't track sub-R milestone timing by default; a user would build this themselves too).
- **Regime analysis**: `mt5_strategies/context.py::classify_market_regime` (ADX/ATR-based 4-bucket classifier) plus `historical_intelligence/segment_matrix.py` for strategy×symbol×regime breakdowns — real, working, forex-specific.
- **Notebooks**: genuinely absent. There is no Jupyter/interactive-notebook environment anywhere in Bensim for ad hoc exploration; the closest analog is the root-level `scratch_*.py` one-off scripts (five of which, per the persistence audit, produced no captured output — `scratch_adaptive_inventory.py`, `scratch_policy_comparison.py` remain genuinely open investigations). LEAN's Research Environment (QuantBook in Jupyter, with direct access to the same data/API the backtester uses) is a real, distinct capability Bensim has no equivalent of — not the engine, just the *interactive research workflow*.
- **Parameter surfaces / performance attribution**: `research_autopilot/attribution.py` exists (unapplied to MT5, per §2/§3's pattern) — factor-style attribution for a cross-sectional equity panel, not directly reusable for a single-symbol forex strategy without rework.
- **Visualization**: no dedicated charting/report generation for MT5 strategy diagnostics found in the backend; whatever exists is presumably frontend-side (`StrategyPerformanceDashboard.tsx`, `StatisticalLab.tsx`, etc., per the task brief) — this document did not find a corresponding backend route currently registered for those pages in `backend/api/router.py` for the MT5 domain specifically.

**Net assessment:** the one real, distinct, worth-adopting-the-concept-of capability here is the **notebook-style ad hoc research workflow** — not because Bensim lacks statistical tooling (it doesn't), but because it lacks a low-friction, session-persistent way to explore the fingerprint/outcome corpus interactively instead of writing a new one-off `scratch_*.py` script (many of which are later found to have no captured output) each time a question comes up.

## 8. Performance analytics

- **Already computed, well**: Sharpe/Sortino/Calmar/CAGR/max-drawdown/turnover/stability (`model_lab/metrics.py`, unapplied to MT5 — same pattern as above); win-rate/expectancy-R/median-R/profit-factor/MFE/MAE/immediate-failure-rate/sequential-max-drawdown-R (`walk_forward.py::_stats_for_rows`, **this one IS applied to real MT5 outcome data**); PSR/DSR/min-track-record-length/bootstrap-CI (`robustness/scorecard.py`, unapplied).
- **Not computed anywhere for MT5 strategies**: VaR/CVaR, alpha/beta (not meaningful for a single-instrument-class forex system without a benchmark — correctly absent, not a gap), information ratio (same), drawdown *duration* (only drawdown *magnitude* is tracked; how long a strategy stays underwater is not), recovery factor, rolling (time-windowed, not split-windowed) performance, monthly/yearly consistency tables.
- **Which of these should actually gate strategy approval** (the user's explicit ask — not decoration): expectancy-R and win-rate already do (via `entry_intelligence`'s reliability gate and `walk_forward`'s directional-edge gate) — correct, since R-multiple expectancy is the metric that actually answers "does this edge exist." PSR/DSR *should* gate approval once wired to real strategy data — they directly answer "is this edge statistically distinguishable from noise," which expectancy-R alone does not. Sharpe/Sortino/Calmar are secondary — useful for comparing strategies to each other, not for a go/no-go decision on any one strategy, and should not be given veto power. VaR/CVaR would matter more once portfolio-level (multi-strategy, multi-symbol) backtesting exists (§4) than they do per-strategy today.

**Net assessment:** no new metric needs to be invented or copied from LEAN — the correct move is applying metrics Bensim already has code for (PSR/DSR specifically) to the data that actually matters, and adding drawdown-duration/recovery-factor as small, native additions to `walk_forward.py::_stats_for_rows`.

## 9. Strategy lifecycle

Bensim has real *pieces* of a lifecycle, but no single formal state machine:

- **Activation states exist**: `ACTIVE_MT5` / `SHADOW_MT5` / `DISABLED` (`mt5_strategies/models.py`), enforced live.
- **A human-approved promotion/demotion loop exists and is genuinely well-designed**: `mt5_strategies/performance_monitor.py` (new, 2026-08-18) computes real trade-level $P&L (for ACTIVE strategies) or shadow-tracked outcomes (for SHADOW/DISABLED strategies) over a rolling 14-day window, and writes a `PENDING_REVIEW` recommendation — asymmetric thresholds (harder to reinstate than to flag), never auto-executes, never touches `.env`/activation flags itself. This is a real, working analog to a lifecycle *transition mechanism*, just not framed as a named state machine.
- **A policy-archetype layer exists**: `adaptive_management/policy_library.py`'s `ARCHETYPE_POLICIES` carry a `validation_status: "research"` field and a `minimum_data_requirements` gate — the *vocabulary* of a lifecycle ("research" as a status) is already present but not connected to a formal progression.
- **Trust gating exists as a strategy-level state**: `trust_gating.py`'s ACTIVE/not-ACTIVE classification (n≥20 and exact-match≥50% OR exact+direction≥70%) is itself a real go/no-go gate, currently showing most strategies below the ACTIVE bar (per the persistence audit's live table) — this is functionally a lifecycle checkpoint already, just not labeled as one.
- **What's missing**: a single, explicit, named state machine (the user's proposed `IDEA → BACKTESTED → ROBUSTNESS_TESTED → OUT_OF_SAMPLE_PASSED → LEAN_VALIDATED → DEMO → LIVE_ELIGIBLE → LIVE → DEGRADED → SUSPENDED → RETIRED` or similar) that ties trust-gating + walk-forward edge-stability + directional-edge + PSR/DSR (once wired) + performance-monitor recommendations into one authoritative status per strategy, with an audit trail of transitions. Today these signals exist independently and a human has to mentally combine them.
- **Does QuantConnect/LEAN have a concept that makes this stronger?** Only loosely. LEAN itself has no strategy-lifecycle concept — it backtests one algorithm at a time; QuantConnect Cloud's "Live Trading" vs "Backtesting" vs "Optimization" project states are a workflow UI distinction, not a governed state machine with promotion criteria. There is nothing here worth adopting from LEAN specifically — this is a native design problem, informed by (but not solved by) the individual gate signals Bensim already computes.

## 11. Top 10 capabilities Bensim should adopt, ranked by actual expected benefit

1. **Realistic spread + commission cost in historical outcome labeling** (`outcomes.py`). Every downstream statistic — walk-forward expectancy, ESS, trust-gating — is currently computed mostly gross-of-cost. This single change re-grades the honesty of every gate Bensim already has, without adding a new gate.
2. **Wire `robustness/scorecard.py` (DSR/PSR/bootstrap) to real per-strategy R-multiple sequences** from `historical_setup_outcomes` / live closed-trade data. This directly answers "is this edge statistically distinguishable from noise," which expectancy-R alone cannot — and the code to do it already exists and is correct.
3. **Wire `model_lab/montecarlo.py` (block-bootstrap Monte Carlo) to the same R-multiple sequences** — produces a real drawdown-distribution and probability-of-ruin-style view per strategy, again from code that already exists.
4. **Formal, unified strategy lifecycle status** combining trust-gating + walk-forward edge-stability + directional-edge + (once wired) DSR verdict + performance-monitor recommendations into one authoritative, auditable per-strategy state with a transition log.
5. **Independent second-engine cross-check using LEAN**, scoped narrowly (see §12) — not as a replacement for Bensim's replay, but as an occasional, offline sanity check on a subset of strategies/symbols where disagreement would be genuinely informative.
6. **Parameter-plateau / robustness-favoring optimization** — evaluate whether a strategy's edge holds across a neighborhood of its parameters, not just at one best-fit point. Native build; LEAN doesn't have this either.
7. **Retrospective/backtested portfolio-level margin, exposure, and correlation** across the strategy/symbol mix over historical time — extends `portfolio_execution/service.py`'s already-strong live accounting backward, not sideways to LEAN.
8. **A lightweight interactive research workflow** (even a simple persistent notebook or query console against the fingerprint/outcome/walk-forward tables) to replace the pattern of one-off `scratch_*.py` scripts, several of which have already been lost with no captured output.
9. **Drawdown duration and recovery factor**, added to `walk_forward.py::_stats_for_rows` alongside the existing sequential-drawdown-R calculation — small, cheap, closes a real reporting gap.
10. **Extend the existing grid-search sweep (`model_lab::param_sweep`) to MT5 strategy parameters**, once the walk-forward/DSR wiring above exists to judge sweep results by robustness rather than best historical point-estimate.

## 12. Top 5 things Bensim should NOT adopt

1. **Do not integrate the full LEAN engine as Bensim's primary backtester.** Bensim's real strength — point-in-time replay of its *actual production strategy code* against MT5-specific data-integrity fixes LEAN has no exposure to — cannot be replicated by moving to a generic engine. Replacing `replay.py`/`outcomes.py` with LEAN would mean re-deriving, inside LEAN, everything the two audits in this repo confirm Bensim already got right (bar-overwrite fix, broker-UTC-offset fix, no-lookahead enforcement) — a strictly worse position, not a better one.
2. **Do not adopt genetic/Bayesian/evolutionary optimization on the theory that "QuantConnect has it."** It doesn't — QuantConnect Cloud ships grid search only, confirmed directly against current docs. Chasing an optimization technique neither platform has shipped, for a strategy set of 11 hand-built families (not a large sweepable parameter space), is effort with no clear payoff right now.
3. **Do not subscribe to QuantConnect Cloud for data, compute, or optimization.** Nothing QC Cloud offers (grid-search compute, its data library, its live-trading nodes) addresses Bensim's actual gaps — the gaps are in cost-realism and application of statistics Bensim already has code for, not in compute capacity or data breadth. QC Cloud pricing (roughly $120/month for a usable live-trading tier, plus $24+/month per live node, plus per-hour backtest compute overages) buys capability Bensim doesn't need and creates exactly the "dependent on QuantConnect Cloud" outcome the user explicitly ruled out.
4. **Do not build a general-purpose, LEAN-style Algorithm Framework (alpha/portfolio-construction/execution/risk model abstraction layers) for Bensim's 11 strategy families.** That abstraction earns its cost when a platform must support many heterogeneous strategies across many asset classes and brokers over years. Bensim has a small, fixed set of forex strategies against one broker; the `context.py` → `families.evaluate_all` → `fusion.build_candidates` pipeline already gives each family a shared, consistent feature contract without the overhead of a pluggable-model framework.
5. **Do not add exchange-calendar/corporate-actions/symbol-mapping infrastructure.** These solve equity/futures problems (holidays, splits, dividends, ticker changes) that spot forex structurally does not have. `market_structure/sessions.py` already encodes the session structure (Asian/London/NY) that actually matters for forex.

## 13. Architecture recommendation

**Combine — with LEAN's role deliberately narrow.** The correct posture is:

- For everything in §11 items 1–4 and 6–10: **B (native)**. These are either extensions of modules Bensim already owns and already got right, or native builds that LEAN doesn't itself provide (parameter-plateau optimization, unified lifecycle, retrospective portfolio backtest). Full LEAN integration would not accelerate any of these — most of the *code* already exists in Bensim's own repo, disconnected. The work is wiring, not engine adoption.
- For **one narrow, specific use** — an independent second-opinion cross-check on execution-cost-sensitive strategies — **A (integrate LEAN as an offline worker)** is justified, detailed in §14 below. This is the only place in the entire analysis where "run LEAN inside Bensim" clears the bar of "genuinely improves Bensim" rather than "QuantConnect has it, so adopt it."
- **C (QuantConnect Cloud) is not recommended anywhere.** Every capability QC Cloud would sell Bensim (compute, data, grid-search optimization, live-trading nodes) either already exists natively in Bensim, is not actually more advanced on QC Cloud than what Bensim already has, or is irrelevant to Bensim's single-broker, single-asset-class, currently-demo-only trading scope. Introducing a paid external dependency for capability Bensim doesn't lack fails the user's own stated constraint.

## 14. LEAN integration feasibility: independent validation

**Is it technically realistic?** Yes, with real caveats, for a narrowly-scoped purpose — not as Bensim's primary or even secondary backtester, but as an occasional, offline, independent cross-check.

**Licensing.** Confirmed directly from `github.com/QuantConnect/Lean/blob/master/LICENSE`: the LEAN engine itself is licensed **Apache 2.0** — permissive, explicitly allows commercial use, modification, and self-hosting without royalty or compliance obligation. `lean-cli` (the tool for running LEAN locally/in Docker) is separately open-sourced (`QuantConnect/lean-cli`) under a compatible license. Running LEAN as a local worker process inside Bensim's own infrastructure creates **no dependency on QuantConnect Cloud** and no ongoing cost — this satisfies the user's explicit constraint ("do NOT make Bensim dependent on QuantConnect Cloud if the open-source LEAN engine can provide the capability locally").

**Proposed architecture, exactly as the user sketched it:** Bensim → Validation Orchestrator → LEAN Worker (Docker, `lean backtest`, invoked as a subprocess/batch job, never in the live decision path) → Results Adapter (parses LEAN's JSON backtest output into Bensim's own metric vocabulary — R-multiples, win rate, expectancy — since LEAN's native output is $-P&L/Sharpe-oriented) → Bensim Validation Database (a new, small table: `lean_cross_check_results`, keyed by strategy_id/symbol/period, storing both engines' verdicts side by side).

**What LEAN would actually validate, and what it would not:**
- LEAN **can** independently re-simulate a *simplified, translated* version of a Bensim strategy's entry/exit rule (e.g., "MT5 EMA-trend pullback with these ATR-based SL/TP levels") using LEAN's own fill/slippage/spread models against LEAN's own forex data source. This is a genuinely independent second opinion on execution-cost sensitivity — exactly the value the user is after.
- LEAN **cannot** replay Bensim's actual production Python (`mt5_strategies/families/*.py`, `context.py`) — those are Bensim-specific and not portable into LEAN's algorithm interface without a full manual reimplementation of every strategy family in LEAN's own algorithm class structure (C#/Python `QCAlgorithm` subclass). This reimplementation is real, non-trivial work per strategy family, and it introduces exactly the risk the cross-check is meant to catch: a translation bug in the LEAN copy would look like a "disagreement" when it's actually just an inaccurate port. **This is the central technical caveat**: the cross-check's value depends entirely on how faithfully each strategy family gets reimplemented in LEAN, and that reimplementation is manual, ongoing maintenance (every change to a Bensim strategy would need a matching LEAN-side change to stay comparable).
- **Data source choice matters and should be deliberate, not default.** Two configurations are meaningfully different: (a) feed LEAN Bensim's own MT5 canonical candles via LEAN's custom-data import path, isolating *engine/fill-model* differences from *data* differences — the more useful configuration for diagnosing "is our fill/spread assumption wrong," and (b) let LEAN use its own independently-sourced forex data (Oanda/Dukascopy-derived, depending on what LEAN's data library offers for forex), which additionally tests whether Bensim's own MT5 broker-quoted history has any broker-specific quirks — more valuable for data-integrity cross-validation, but conflates two different sources of disagreement. **Recommendation: start with (a)** (same data, different engine) since it isolates exactly the execution-simulation question this document identifies as the highest-value gap; only pursue (b) later if (a) proves the workflow's value.

**When disagreement should trigger investigation** (per the user's own list — fills, spread, slippage, candle timing, order sequencing, look-ahead bias, fees, position sizing, timezone/session handling): this is the right checklist, and Bensim's own `outcomes.py`/`replay.py` docstrings already name several of these as *known, documented approximations* (spread=0 default, no commission) rather than unknowns — so a first cross-check run would likely surface exactly the gap already identified in §1/§5, which is a good sign the exercise would validate real findings rather than manufacture spurious ones.

**Is it worthwhile?** For a small number of strategy families and one or two symbols (start with `ema_trend` or `mean_reversion` on EURUSD, the symbols with the deepest corpus today), yes — the Apache 2.0 license and local Docker deployment make it low-cost and reversible, and it directly stress-tests the exact spread/cost-realism gap this document already flagged as highest-value. Committing to reimplementing and maintaining all 11 strategy families inside LEAN indefinitely would not be worthwhile — the maintenance burden would likely exceed the value once the initial cross-check has done its job of confirming (or correcting) Bensim's own cost-realism assumptions.

## 15. Phased roadmap

Every phase below is designed to run alongside, and not touch, the ongoing cTrader migration or any file under `backend/brokers/mt5/`, `backend/mt5_strategies/`, `backend/historical_intelligence/`, `backend/portfolio_execution/`, or `backend/adaptive_management/` in a way that changes live trading behavior. Phases 1–2 are additive-only (new logic reading existing tables); nothing here proposes touching any existing statistical threshold (ESS≥100, similarity floor, purge window, etc.) — consistent with both prior audits' explicit "out of scope" sections.

**Phase 1 — Cost-realism and statistics wiring (no live-behavior change).**
Extend `outcomes.py` to estimate spread/commission more broadly (not only when a decision snapshot exists) using the same real-broker-observed cost basis `trading_costs.py` already established for live deals; wire `robustness/scorecard.py` and `model_lab/montecarlo.py` to real per-strategy R-multiple sequences from `historical_setup_outcomes`; add drawdown-duration/recovery-factor to `walk_forward.py::_stats_for_rows`. Output: new, more honest numbers annotated alongside existing gates — no threshold changes, no live-path changes. This directly continues the pattern already established by the two prior audits (compute honestly, gate conservatively, don't touch live trading).

**Phase 2 — Unified strategy lifecycle status (annotation-only, then human-gated).**
Build the single authoritative per-strategy status combining trust-gating + walk-forward edge-stability/directional-edge + (Phase 1's) DSR verdict + performance-monitor recommendations, with a transition audit log. Initially read-only/dashboard-only, mirroring how `performance_monitor.py` was deliberately shipped as recommendation-only with a human sign-off gate — no automatic activation changes.

**Phase 3 — Native robustness and portfolio-backtest builds.**
Parameter-plateau/robustness-favoring optimization report; retrospective/backtested portfolio-level margin-exposure-correlation view extending `portfolio_execution/service.py`'s live accounting backward in time; a lightweight interactive research workflow to replace ad hoc `scratch_*.py` scripts. All native, no external dependency.

**Phase 4 — Scoped, offline LEAN cross-check (experimental, isolated).**
Stand up LEAN via Docker/`lean-cli` as a fully offline worker with no code or network path into the live trading container; hand-port 1–2 strategy families (starting with the simplest, e.g. `ema_trend`) into LEAN's algorithm interface fed with Bensim's own MT5 canonical candle data; build the Results Adapter and a small `lean_cross_check_results` table; run a first comparison against Phase 1's now-cost-realistic Bensim numbers. Treat this phase as a validation experiment with an explicit stop/continue decision at the end, not a committed long-term integration — expand to more strategies only if the first comparison proves informative enough to justify the ongoing per-strategy maintenance cost identified in §14.

**Sequencing rationale:** Phase 1 is the highest-value, lowest-risk, smallest-scope work and should happen regardless of anything else in this document. Phase 4 (the only LEAN-touching phase) is deliberately last and explicitly experimental — it should not start until Phase 1's cost-realism fix exists, because otherwise a LEAN-vs-Bensim disagreement on spread/cost would just be re-discovering a gap this document has already identified from source, at needless extra effort.
